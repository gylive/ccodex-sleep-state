## 本轮：OAuth 请求压缩兼容问题

真实 OAuth 联调的第一轮发现：恢复官方 provider 名称后，Codex 会发送 `Content-Encoding: zstd` 请求；旧代理只收未压缩 JSON，直接返回本地 415。该轮在进入模型链路前停止，实际模型尝试 **0 次**，不能把它写成“上游故障”。

随后加入 identity / gzip / zstd 解码，压缩输入和解压后正文均限制 16 MiB，zstd 窗口也设上限。解码之后仍校验 JSON、模型和 V2 压缩操作，移除旧编码声明再转发。

`encoding_test.go` 已覆盖并通过：生成解码转发、V2 识别、损坏/截断编码、未知及叠加编码、压缩与解压超限、zstd 超大窗口和模型限制。修复后的真实 OAuth 结果已列在上面的 11 次账本中：zstd 不再把这些请求拦在本地 415；Astra 后续两次短回复成功，但 292 和 V1 真实桥接仍未完成。请求编码修好不等于所有业务验收通过。

真实 Codex CLI → Go 服务 → 内嵌 AnyTLS 出站 → 真实 Astra 上游

- 使用独立的 Codex 目录和测试工作目录，由服务备份并配置 provider。

## 前面遇到的问题与修复

第一次只测直连，返回的是 312；后来用另一组真实出口，也没有采到默认基线。将独立测试配置临时改为 11 块时，曾验证过注入协议能通，但这不算默认规则验收。上面的 292 实测才是后续结果。

排查发现并修复了这些实现问题：

- **AnyTLS 漏支持。** 现在 YAML、URI 导入均接入内嵌核心，有解析/构造测试和上述真实联调。
- **下载客户端标识影响订阅内容。** 可以逐条订阅设置 `user_agent`；空 `proxies` 会给出明确错误，不再混成编码错误。
- **需要明确选节点。** 增加协议白名单和名称/地址关键词排除，先过滤、再创建连接；不必为了混合订阅关闭 TLS 校验。
- **首条请求等备用采集。** 现在拿到第一份合格 state 就转发，备用采集留给后台并受冷却限制。
- **正式请求的账号错误没有统一暂停。** 现在探测与正式请求共享 401/403/429 处理，暂停期间不会因为已有 active 就继续发请求。
- **探测请求与源网关的 Codex 封装有差异。** 补齐 Responses 附加字段，不再强制 `low` 思考参数。单独对照这一改动时仍出现过 312，不能声称仅靠这项改动就能采到 292。

## 遇到 `state_unavailable`

看日志中的 `probe_finished`，不要连续重发：

- `result: "shape_mismatch"`：请求完成了，但 `state_blocks` 不等于 `expected_blocks`。这是没采到符合规则的值，不等于节点断网。
- `result: "state_time_rejected"`：封装可读，但时间不符合本地规则。
- `result: "request_failed"`：连接、封装解析或 SSE 完成检查失败，结合状态码排查。

`status` 的 `phase` 会区分等待 state、已就绪、认证暂停和限流等待。历史版本没有合格值时保持严格模式。本轮转发内核空策略仍严格，但首次 `setup` 无明确策略时采用普通转发兜底，并保留用户已明确的 `strict`；它不注入不合格 state，也不把 312 当成 292 使用。
